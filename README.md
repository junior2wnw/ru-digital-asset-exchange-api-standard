# RU Digital Market Interoperability Profile

**RU-DMIP — открытый технический стандарт для подключения систем цифрового финансового рынка через единый проверяемый API-контракт.**

Он нужен, чтобы банк, брокер, торговая площадка, оператор цифровых прав, кастодиан, учетная система или разработчик не согласовывали заново одни и те же сущности, статусы, ошибки и правила безопасности при каждом новом подключении.

Проще говоря: участники сохраняют собственные продукты и внутренние системы, но одинаково отвечают на базовые вопросы внешней интеграции:

- какие возможности доступны;
- как отправить команду и безопасно повторить ее;
- как понять состояние заявки, перевода или права;
- как проверить полномочия;
- как получить однозначную ошибку;
- как доказать совместимость автоматическими тестами.

RU-DMIP — не единая платформа, не новая биржа и не обязательная библиотека. Это общий язык на границе независимых систем.

> Статус: **Draft 0.5 для технической оценки и пилотов**. Проект не является нормативным актом, лицензией, юридическим заключением или позицией государственного органа.

## Зачем нужен общий контракт

Сегодня интеграция обычно зависит не только от адресов API и названий полей. Для каждого нового участника приходится выяснять, что означает статус, когда команда считается принятой, можно ли повторить запрос, какие данные актуальны и какое действие действительно разрешено.

RU-DMIP выносит эту повторяющуюся часть в открытый контракт:

| Без общего профиля | С RU-DMIP |
| --- | --- |
| для каждого подключения создается отдельная логика | общая клиентская логика используется повторно |
| одинаковые статусы могут означать разное | состояния и события имеют зафиксированный смысл |
| особенности повторов выясняются после ошибок | идемпотентность и конфликты определены заранее |
| совместимость подтверждается документацией или обещанием | совместимость подтверждается исполняемыми тестами |
| технический доступ легко принять за правовой допуск | правовые ограничения и ответственность отделены от возможностей API |
| защищенные данные могут попадать в лишние контуры | используются минимальные данные, ссылки, хеши и разграничение доступа |

Стандарт не устраняет различия между участниками. Он устраняет необходимость каждый раз изобретать заново то, что не создает конкурентного преимущества, но создает стоимость и риск.

## Что именно стандартизируется

| Область | Что получает интеграция |
| --- | --- |
| Возможности участника | роли, версия, поддерживаемые модули и ограничения через `/v1/profile` |
| Рыночные данные | единые модели инструментов, стакана, сделок и свечей |
| Торговля и исполнение | заявки, состояния, события, комиссии, лимиты, повторы и восстановление цепочки событий |
| Учет и хранение | активы, адреса, вводы, выводы, внутренние переводы и подтверждения |
| Производные инструменты | позиции, маржа, финансирование, расчеты и FIX-совместимый профиль |
| Контроль и отчетность | согласия, аудит, статусы проверок и ссылки на защищенные отчеты |
| Права и полномочия | требования, ограничения, обременения, доказательства и решение о допустимости действия |

Каждая реализация публикует только то, что действительно поддерживает. Клиент сначала читает профиль возможностей и не делает предположений по названию организации или типу продукта.

## Кому это дает практический результат

| Участник | Что меняется |
| --- | --- |
| Поставщик API | одна стабильная внешняя граница вместо отдельного контракта под каждого партнера |
| Банк или брокер | повторно используемые модели, проверки и обработка ошибок при следующем подключении |
| Торговая площадка или оператор | понятный путь проверки совместимости без раскрытия внутренней архитектуры |
| Кастодиан или цифровой депозитарий | однозначный жизненный цикл движения, учета и подтверждения прав |
| ОИС, ООЦФА или эмитент | структурированное описание прав, ограничений и доказательств без публикации лишних документов |
| Разработчик | меньше условной логики, зависящей от конкретного поставщика |
| Информационная безопасность | единые требования к подписи, повторам, полномочиям и журналированию |
| Комплаенс и аудит | машиночитаемые статусы и воспроизводимая цепочка событий вместо свободного текста |
| Рабочая группа | предмет обсуждения, который можно запустить, проверить и улучшить |

## Почему это не просто документация

Репозиторий содержит четыре взаимосвязанных слоя:

1. **Спецификация** фиксирует смысл объектов, состояний и поведения.
2. **OpenAPI и JSON Schema** дают машиночитаемую форму контракта.
3. **Эталонные клиенты и песочница** показывают рабочее поведение.
4. **Тесты совместимости** проверяют, соответствует ли реализация заявленному уровню.

Иными словами, описание можно не только прочитать, но и исполнить. Если две независимые реализации проходят один набор проверок, существенная часть интеграции становится переносимой между ними.

## Уровни совместимости

Профиль внедряется поэтапно. Необязательно поддерживать его целиком.

| Уровень | Проверяемый контур |
| --- | --- |
| L0 | описание участника, доступных возможностей и единый формат ошибок |
| L1 | публичные рыночные данные |
| L2 | торговые команды и жизненный цикл исполнения |
| L3 | операции учета, хранения и движения активов |
| L4 | производные инструменты и профессиональный доступ |
| L5 | согласия, аудит, отчетность, права, аутентификация и авторизация |

Заявленный уровень означает только проверенную поверхность API. Он не является лицензией, рейтингом надежности или подтверждением допустимости продукта.

## Безопасность по умолчанию

Эталонный контракт требует для приватных запросов:

- ключ доступа, временную метку и подпись запроса;
- короткое окно действия подписи и защиту от повторного воспроизведения;
- ключ идемпотентности для команд;
- стабильную ошибку конфликта при повторном использовании ключа с другим содержанием;
- разграничение полномочий и усиленную проверку для чувствительных действий;
- журналирование и минимизацию передаваемых данных.

Действия с правами и полномочиями по умолчанию запрещены, пока реализация не подтвердила основание, требуемый уровень аутентификации и применимые ограничения. Публичный API не должен возвращать паспорта, сырые юридические документы или иные защищенные данные.

Подробная модель угроз и требования приведены в [документе по безопасности](docs/SECURITY.md).

## Правовая граница

RU-DMIP учитывает российский правовой контур, но не пытается заменить его.

Профиль разделяет:

- возможность системы и право организации на деятельность;
- техническую роль и юридический статус;
- запись о праве и само возникновение права;
- ссылку на доказательство и защищенный документ;
- поведение песочницы и допустимость промышленной операции;
- отчет о совместимости и регуляторный допуск.

Правовая дата-срезка, источники и ограничения собраны в [RU_LEGAL_ALIGNMENT.ru.md](docs/RU_LEGAL_ALIGNMENT.ru.md).

- OpenAPI и JSON Schema;

## Проверка за 10 минут

Требуются Python 3.10+ и Node.js 20+.

Терминал 1:

```powershell
cd mock-exchange
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install .
uvicorn ru_dmip_mock.app:app --port 8080
```

Терминал 2:

```powershell
cd tests/conformance
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install .
pytest --base-url http://127.0.0.1:8080 --api-key sandbox-key --api-secret sandbox-secret
```

Для ручной проверки импортируйте
[`postman/RU-DMIP.postman_collection.json`](postman/RU-DMIP.postman_collection.json).

Python:

```python
from ru_dmip import Client

client = Client(
    "http://127.0.0.1:8080",
    api_key="sandbox-key",
    api_secret="sandbox-secret",
)

print(client.profile())
print(client.instruments())
print(client.balances())
```

TypeScript:

```ts
import { RuDmipClient } from "@ru-dmip/sdk";

const client = new RuDmipClient({
  baseUrl: "http://127.0.0.1:8080",
  apiKey: "sandbox-key",
  apiSecret: "sandbox-secret",
});

console.log(await client.profile());
console.log(await client.instruments());
console.log(await client.balances());
```

## Как начать пилот

Для первой проверки не нужно принимать весь стандарт. Достаточно:

1. выбрать один реальный, но обезличенный сценарий;
2. сопоставить внутренние сущности и состояния с RU-DMIP;
3. запустить подходящий набор тестов;
4. зафиксировать совпадения, расхождения и необходимые расширения;
5. повторить тот же сценарий на второй независимой реализации.

Практический критерий прост: второе подключение должно требовать меньше специальной логики, чем первое, без потери безопасности, смысла операций и правовых ограничений.

Готовый формат работы приведен в [PILOT.ru.md](docs/PILOT.ru.md).
