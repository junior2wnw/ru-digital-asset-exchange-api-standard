# Единый открытый API-профиль для инфраструктуры цифровых активов

Версия: Draft 0.2

Этот документ описывает независимый технический draft. Он не является нормативным актом, юридической консультацией или официальной позицией регулятора.

## 1. Проблема Фрагментации API

Рынок цифровых активов, цифровой валюты, цифрового рубля, ЦФА, открытых API и производных инструментов развивается как набор независимых площадок и сервисов. У каждой площадки могут отличаться:

- REST endpoints;
- WebSocket streams;
- форматы ордеров и сделок;
- статусы заявок;
- ошибки;
- лимиты;
- комиссии;
- wallet flows;
- правила маржи и деривативов;
- sandbox-поведение.

Для отдельного разработчика это неудобство. Для инфраструктуры рынка это операционный риск: интеграция дорожает, совместимость проверяется вручную, а мониторинг и аудит становятся фрагментированными.

## 2. Риски Для Надзора И Участников

Фрагментация API создает несколько классов риска.

**Операционный риск.** Брокеры, банки, финтех-компании и инфраструктурные провайдеры пишут отдельные адаптеры под каждую площадку. Чем больше адаптеров, тем больше ошибок, задержек и отказов.

**Рыночный риск.** Несовместимые модели лимитов, маржи, funding, settlement и позиций усложняют управление риском на деривативах.

**Надзорный риск.** Если каждая площадка использует свой формат событий, сложнее строить единый мониторинг, сравнивать исполнение, проверять инциденты и анализировать системные риски.

**Пользовательский риск.** Разные статусы выводов, депозитов, ошибок и комиссий ухудшают прозрачность для пользователя.

## 3. Международные Аналоги

В традиционных рынках давно используются общие протоколы и профили:

- FIX для профессиональных участников;
- OpenAPI для REST-интеграций;
- JSON Schema для контрактов данных;
- sandbox и certification tests для банковских и платежных API;
- единые профили отчетности и аудита в регулируемых сегментах.

Цифровые рынки часто используют эти подходы частично. Предлагаемый draft объединяет их в один проверяемый API-профиль.

## 4. Предлагаемая Архитектура

Профиль делится на 12 модулей:

1. REST API.
2. WebSocket market data.
3. WebSocket private events.
4. FIX-compatible profile для профессиональных участников.
5. Единая модель ордеров.
6. Единая модель сделок.
7. Единая модель балансов.
8. Единая модель ошибок.
9. Единая модель комиссий.
10. Единая модель лимитов.
11. Sandbox/testnet.
12. Conformance tests.

Архитектура разделяет контракт и реализацию:

- спецификация описывает технические требования для заявленного уровня совместимости;
- OpenAPI и JSON Schema дают машинную проверку;
- SDK снижает цену входа и показывает reference behavior;
- mock exchange помогает тестировать клиентов;
- conformance suite проверяет совместимость реальных площадок.

## 5. Требования Безопасности

Минимальный security profile:

- TLS 1.3 или актуальный допустимый профиль для production;
- API keys с разделением scopes;
- подпись приватных REST-запросов;
- timestamp и replay protection;
- idempotency key для торговых и wallet-команд;
- IP allowlist для институциональных клиентов;
- WebSocket authentication challenge;
- rate limits с машинно читаемыми заголовками;
- audit trail для ордеров, сделок, балансов и wallet-событий;
- отдельные ключи для sandbox и production;
- запрет передачи секретов в query string.

## 6. Модель Совместимости

Совместимость должна проверяться не декларацией, а тестами.

Уровни:

- L0 Discovery: базовая доступность и единые ошибки.
- L1 Market Data: публичные REST и WebSocket данные.
- L2 Trading: ордера, сделки, комиссии, лимиты, idempotency.
- L3 Wallet & Custody: депозиты, выводы, адреса, transfers, subaccounts.
- L4 Derivatives & FIX: позиции, маржа, funding, settlement, FIX-compatible profile.

Площадка может внедрять уровни постепенно. Это делает стандарт строгим по контракту, но реалистичным по пути внедрения.

## 7. План Пилота За 6 Месяцев

**Месяц 1.** Публичный draft, базовый OpenAPI, JSON Schema, mock exchange, SDK skeleton.

**Месяц 2.** REST market data, trading model, wallet model, первые conformance tests.

**Месяц 3.** WebSocket market data и private events, расширенные SDK, Postman collection.

**Месяц 4.** Derivatives profile: futures, perpetuals, options, margin, funding, settlement.

**Месяц 5.** FIX-compatible profile, security review, pilot checklist, compatibility badges.

**Месяц 6.** Пилот с участниками рынка, юридическая редакция, security review report, публичные conformance reports.

## 8. Выгоды

**Для государства и надзора.** Единая техническая поверхность для отчетности, аудита, мониторинга и анализа системных рисков.

**Для бирж.** Снижение стоимости интеграций, понятный certification path, доверие профессиональных участников.

**Для брокеров и банков.** Один клиентский слой вместо набора нестабильных адаптеров.

**Для custody и wallet-провайдеров.** Единые статусы операций, адресов, сетей, transfers и compliance metadata.

**Для пользователей.** Более прозрачные комиссии, статусы, операции с кошельком и предсказуемое качество сервиса.

**Для разработчиков.** Низкий порог входа: SDK, схемы, mock exchange и conformance tests доступны сразу.

## 9. Практическая Формула

Не нужно добиваться формулировки "использовать конкретную библиотеку". Это создает сопротивление и выглядит как частный интерес.

Нужно добиваться открытой совместимости:

| Цель | Реалистичность | Эффект |
| --- | --- | --- |
| Принцип единого открытого API в публичной политике | Средняя | Высокий |
| Технические требования в акте регулятора | Средняя/высокая | Очень высокий |
| SDK как open-source reference implementation | Высокая | Максимальный вход на рынок |

Оптимальная последовательность:

1. Подготовить нейтральный draft.
2. Доказать реализуемость через SDK, mock exchange и тесты.
3. Провести отраслевой пилот.
4. Получить юридическую и security-экспертизу.
5. После этого предлагать регуляторную формулировку.
