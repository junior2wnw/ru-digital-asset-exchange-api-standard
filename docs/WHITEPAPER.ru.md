# Единый открытый API для регулируемого рынка цифровой валюты РФ

Версия: Draft 0.1

## 1. Проблема фрагментации API

Криптовалютные и цифровые финансовые рынки исторически развивались как набор независимых площадок. У каждой площадки свои:

- REST endpoints;
- WebSocket streams;
- форматы ордеров и сделок;
- статусы заявок;
- ошибки;
- лимиты;
- комиссии;
- wallet flows;
- правила деривативов;
- sandbox-поведение.

Для обычного рынка это неудобство. Для регулируемого рынка это инфраструктурный риск: интеграция становится дорогой, проверка совместимости ручной, а надзор не получает единой технической поверхности.

## 2. Риски для ЦБ и участников

Фрагментация API создает несколько классов риска.

**Регуляторный риск.** Если каждая площадка использует свой формат событий, сложнее строить единый мониторинг, сравнивать исполнение, проверять best execution и расследовать инциденты.

**Операционный риск.** Брокеры, банки и финтех-компании вынуждены писать отдельные адаптеры под каждую площадку. Чем больше адаптеров, тем больше ошибок, задержек и отказов.

**Рыночный риск.** Несовместимые модели лимитов, маржи и позиций усложняют управление риском на деривативах.

**Потребительский риск.** Разные статусы выводов, депозитов, ошибок и комиссий ухудшают прозрачность для пользователя.

## 3. Международные аналоги

В традиционных рынках давно используются единые протоколы и профили:

- FIX для профессиональных участников;
- OpenAPI для REST-интеграций;
- JSON Schema для контрактов данных;
- sandbox и certification tests для банковских и платежных API;
- единые профили отчетности и аудита в регулируемых сегментах.

Крипторынок часто использует эти подходы частично. Предлагаемый стандарт объединяет их в один совместимый профиль для цифровой валюты и цифровых активов.

## 4. Предлагаемая архитектура

Стандарт делится на 12 модулей:

1. REST API.
2. WebSocket market data.
3. WebSocket private events.
4. FIX-compatible profile для профессиональных участников.
5. Единая модель ордеров.
6. Единая модель сделок.
7. Единая модель балансов.
8. Единая модель ошибок.
9. Единая модель комиссий.
10. Единая модель лимитов.
11. Sandbox/testnet.
12. Conformance tests.

Архитектура специально разделяет нормативную часть и реализацию:

- стандарт описывает обязательные контракты;
- OpenAPI и JSON Schema дают машинную проверку;
- SDK снижает цену входа;
- mock exchange помогает тестировать клиентов;
- conformance suite проверяет совместимость реальных площадок.

## 5. Требования безопасности

Минимальный профиль безопасности:

- TLS 1.3 для production;
- API keys с разделением scopes;
- подпись приватных REST-запросов;
- timestamp и replay protection;
- idempotency key для торговых и wallet-операций;
- IP allowlist для институциональных клиентов;
- WebSocket authentication challenge;
- rate limits с машинно читаемыми заголовками;
- audit trail для ордеров, сделок, балансов и wallet-событий;
- отдельные ключи для sandbox и production;
- запрет передачи секретов в query string.

## 6. Модель совместимости

Совместимость должна проверяться не декларацией, а тестами.

Уровни:

- L0 Discovery: базовая доступность и единые ошибки.
- L1 Market Data: публичные REST и WebSocket данные.
- L2 Trading: ордера, сделки, комиссии, лимиты, idempotency.
- L3 Wallet & Custody: депозиты, выводы, адреса, transfers, subaccounts.
- L4 Derivatives & FIX: позиции, маржа, funding, settlement, FIX-compatible profile.

Площадка может внедрять уровни постепенно. Это важно: стандарт должен быть строгим, но путь внедрения должен быть реалистичным.

## 7. План внедрения за 6 месяцев

**Месяц 1.** Публичный draft стандарта, базовый OpenAPI, JSON Schema, mock exchange, SDK skeleton.

**Месяц 2.** REST market data, trading model, wallet model, первые conformance tests.

**Месяц 3.** WebSocket market data и private events, расширенные SDK, Postman collection.

**Месяц 4.** Derivatives profile: futures, perpetuals, options, margin, funding, settlement.

**Месяц 5.** FIX-compatible profile, security review, pilot checklist, compatibility badges.

**Месяц 6.** Пилот с участниками рынка, юридическая редакция, пакет для регуляторов и отраслевых ассоциаций.

## 8. Выгоды

**Для государства.** Единая техническая поверхность для надзора, отчетности, аудита и управления системными рисками.

**Для Банка России.** Возможность утвердить требования не с нуля, а на основе открытого стандарта и тестируемой reference implementation.

**Для бирж.** Снижение стоимости интеграций, понятный certification path, доверие профессиональных участников.

**Для брокеров и банков.** Один клиентский слой вместо набора нестабильных адаптеров.

**Для пользователей.** Более прозрачные комиссии, статусы, операции с кошельком и предсказуемое качество сервиса.

**Для разработчиков.** Низкий порог входа: SDK, схемы, mock exchange и conformance tests доступны сразу.

## 9. Практическая юридическая формула

Не нужно добиваться формулировки "использовать конкретную библиотеку". Это создает политическое и юридическое сопротивление.

Нужно добиваться одного из трех:

| Цель | Реалистичность | Выгода |
| --- | --- | --- |
| Единый API в законе | Средняя | Высокая |
| Единый API в акте ЦБ | Высокая | Очень высокая |
| SDK как open-source reference implementation | Высокая | Максимальная для входа на рынок |

Оптимальная формула:

1. Закон говорит: "должен быть единый открытый API".
2. ЦБ утверждает требования.
3. Проект приносит готовый стандарт, SDK и тесты.
4. Рынок использует реализацию, потому что она уже готова, проверяема и открыта.
