# RU Digital Market Interoperability Profile

Версия: Draft 0.5

Этот документ описывает обязательное техническое ядро RU Digital Market Interoperability Profile. Профиль задает внешнее поведение совместимого API, но не определяет внутреннюю архитектуру организации.

Существующие торговые контракты L1-L4 сохраняются для обратной совместимости внутри более широкого профиля рынка. Документ не является нормативным правовым актом. Слова `MUST`, `SHOULD` и `MAY` используются только для проверки заявленного уровня API-совместимости:

- `MUST`: обязательно для заявленного уровня совместимости;
- `SHOULD`: настоятельно рекомендуется, отклонение требует объяснения;
- `MAY`: допустимое расширение.

## 1. Цель

Профиль позволяет независимым системам одинаково понимать основные данные, команды, состояния, ошибки и требования безопасности цифрового финансового рынка.

Он предназначен для API, через которые участники:

- публикуют рыночные и справочные данные;
- принимают торговые и учетные команды;
- учитывают активы, операции, права и ограничения;
- передают статусы проверок и отчетные сведения;
- подтверждают совместимость автоматическими тестами.

Профиль может применяться торговыми площадками, банками, брокерами, операторами цифровых прав, кастодиальными и учетными системами, поставщиками данных, разработчиками, комплаенс-, RegTech- и аудиторскими командами.

RU-DMIP стандартизирует только внешнюю границу. Внутренние системы, продуктовые правила, риск-модели и конкурентные особенности остаются у реализации.

Профиль не должен смешивать техническую совместимость и право деятельности. Если операция, инструмент или данные имеют правовое значение, API должен возвращать структурированный признак или ограничение, а не скрывать его в свободном тексте.

## 2. Базовая архитектура

Реализация предоставляет только компоненты заявленного уровня совместимости:

1. `GET /v1/profile` для ролей, поддерживаемых возможностей, уровней совместимости и правовых контуров.
2. REST API для запросов и команд.
3. WebSocket для публичных потоков рыночных данных.
4. WebSocket для защищенных клиентских событий.
5. FIX-совместимый профиль для профессиональных участников.
6. Единые модели ордеров, сделок, балансов, ошибок, комиссий и лимитов.
7. Универсальную семантику исполнения для намерений, событий, состояний, повторного воспроизведения, синтетических позиций и ограничений риска.
8. Песочницу или тестовую сеть с тем же контрактом, что и промышленная среда.
9. Профиль правомочий и авторизации (`Entitlements & Authorization`) для требований, полномочий, сильной аутентификации и правил доступа.
10. Профиль L5 для согласий, AML/KYC, событий аудита, регуляторной отчетности и валютного контроля.
11. Метод API или публичную инструкцию для запуска тестов совместимости.

## 2.1 Роли участников

Реализация SHOULD публиковать в `/v1/profile` одну или несколько API-ролей:

- `exchange`;
- `broker`;
- `bank`;
- `ois_cfa`;
- `ootsfa`;
- `crypto_exchange`;
- `digital_depository`;
- `management_company`;
- `organized_trading_operator`;
- `custodian`;
- `wallet_provider`;
- `payment_provider`;
- `market_maker`;
- `issuer`;
- `qualified_investor_gateway`;
- `compliance_provider`;
- `analytics_provider`;
- `developer_tool`;
- `regulator_observer`;
- `mining_infrastructure_operator`.

Роль не подтверждает лицензию, включение в реестр или право осуществлять деятельность. Она только описывает API-поверхность, которую заявляет реализация. Одной организации могут соответствовать несколько ролей, а одна роль может быть реализована несколькими типами организаций, если это допускает применимый правовой контур.

## 3. Идентификаторы

Реализация MUST использовать стабильные идентификаторы:

- `instrument_id`: стабильный id инструмента внутри реализации;
- `client_order_id`: idempotent id клиента;
- `exchange_order_id`: id ордера на стороне исполнения;
- `trade_id`: id сделки;
- `account_id`: id аккаунта;
- `subaccount_id`: id субаккаунта;
- `asset_id`: id актива;
- `wallet_transaction_id`: id wallet-операции.

`client_order_id` MUST быть уникален в рамках аккаунта и торгового дня или более длинного окна, указанного реализацией.

Имя `exchange_order_id` сохранено как историческое поле торгового ядра. Клиент не должен выводить из него правовую или организационную роль контрагента.

## 4. Инструменты

Единая модель инструмента MUST покрывать:

- `spot`;
- `margin_spot`;
- `perpetual_future`;
- `dated_future`;
- `option`;
- `swap`;
- `index`;
- `structured_product`.

Каждый инструмент MUST публиковать:

- базовый и котируемый актив;
- статус торговли;
- price tick;
- quantity step;
- min/max order size;
- min notional;
- fee schedule reference;
- risk parameters;
- settlement model для деривативов;
- expiration для срочных инструментов;
- underlying для options и futures.

Инструмент SHOULD публиковать law-aware поля, если они применимы:

- `legal_classification`;
- `regulatory_scope`;
- `investor_access`;
- `payment_use_allowed`;
- `jurisdiction`.

## 5. Ордера

Реализация L2 MUST поддерживать единую модель ордера:

- `market`;
- `limit`;
- `stop_market`;
- `stop_limit`;
- `take_profit_market`;
- `take_profit_limit`;
- `post_only`;
- `ioc`;
- `fok`;
- `reduce_only` для деривативов;
- `close_position` для деривативов.

Статусы:

- `accepted`;
- `open`;
- `partially_filled`;
- `filled`;
- `cancel_pending`;
- `cancelled`;
- `expired`;
- `rejected`.

## 5.1 Универсальная семантика исполнения

Профиль SHOULD публиковать `GET /v1/execution/capabilities`.

Этот метод описывает не коннектор и не внутреннюю реализацию, а общий контракт исполнения:

- поддерживаемые типы намерений;
- автомат состояний исполнения;
- типы событий;
- правила разрешения конфликта отмены и исполнения;
- правила работы с устаревшими данными;
- повторное воспроизведение и восстановление пропущенных событий;
- окно идемпотентности;
- ограничения риска;
- границу, за которой допустима специальная логика конкретного участника.

Клиентская и серверная бизнес-логика SHOULD принимать решения по заявленным возможностям, состояниям, ограничениям риска и контракту исполнения, а не по имени участника или внутреннему типу адаптера.

Профиль считает `spread` самостоятельным типом торгового намерения. Это не пара независимых заявок и не только элемент интерфейса, а структурированное намерение с частями (`legs`), ограничениями, контрактом исполнения, правилами риска и событиями.

- `quantity`;

## 8. Wallet И Custody

- список активов и сетей;
- депозитные адреса;
- историю депозитов;

## 9. Ошибки

Каждая ошибка MUST возвращаться в формате:

```json
{
  "error": {
    "code": "ORDER_INSUFFICIENT_BALANCE",
    "message": "Insufficient available balance",
    "category": "business",
    "request_id": "req_01HZZ...",
    "details": {}
  }
}
```

Код ошибки MUST быть стабильным и машиночитаемым.

## 10. Комиссии И Лимиты

Реализация MUST публиковать применимые комиссии и лимиты:

- maker/taker fees;
- withdrawal fees;
- funding rules;
- settlement fees;
- rate limits;
- order limits;
- position limits;
- notional limits;
- leverage limits.

## 11. Безопасность

Приватные REST-запросы MUST включать:

- ключ API;
- временную метку;
- подпись запроса;
- необязательное одноразовое значение (`nonce`);
- ключ идемпотентности для команд.

Повтор команды с тем же ключом идемпотентности и тем же содержанием MUST возвращать исходный результат. Тот же ключ с другим содержанием MUST завершаться ошибкой конфликта без выполнения команды.

Реализация SHOULD поддерживать:

- список разрешенных IP-адресов;
- ключи с ограниченными полномочиями;
- ключи только для чтения;
- отдельные ключи для торговли и операций с активами;
- институциональные ключи, связанные с FIX-сессиями.

## 12. Расширения

Реализации MAY добавлять поля конкретного поставщика через объект `extensions`, не нарушая базовую схему.

Пример:

```json
{
  "instrument_id": "BTC-RUB-SPOT",
  "type": "spot",
  "extensions": {
    "venue_feature": "custom_value"
  }
}
```

Клиенты MUST игнорировать неизвестные поля, если они не меняют смысл обязательных полей.

## 13. Правовая совместимость РФ

Для реализации в российском правовом контуре API-провайдер SHOULD явно отделять:

- ЦФА, цифровую валюту, цифровой рубль, иностранные цифровые права, ценные бумаги, деривативы и обычные денежные остатки;
- тестовую возможность от допуска к промышленной эксплуатации;
- технический статус операции от AML/KYC, валютного контроля, ограничений доступа инвестора и правил площадки;
- публичные рыночные данные от клиентских, персональных и охраняемых данных.

Минимальные возможности, учитывающие правовые ограничения:

- `aml_kyc`;
- `open_api_consent`;
- `digital_ruble`;
- `cfa_issuance`;
- `cfa_exchange`;
- `crypto_circulation`;
- `fx_control`;
- `entitlements`;
- `strong_authentication`;
- `authorization_policy`;
- `delegated_authority`;
- `tax_reporting`;
- `audit_export`;
- `regulatory_reporting`.

Если возможность зависит от регистрации, лицензии, реестра, правил участника или ЭПР, `/v1/profile` MUST показывать это через `legal_profiles.status`, а не через маркетинговое описание. Статус `supported` означает техническую реализацию и сам по себе не означает правовой допуск.

Значения `legal_profiles.framework_id` являются внутренними идентификаторами RU-DMIP для обнаружения возможностей. Они не заменяют реквизиты нормативного акта; официальные источники и актуальная дата проверки указываются отдельно.

## 14. L5: контроль и отчетность

L5 добавляет защищенный слой совместимости для участников, которым нужны не только торговые команды, но и контролируемый обмен статусами, согласиями, аудитом и отчетными метаданными.

L5 MUST NOT раскрывать персональные данные, банковскую тайну, коммерческую тайну, сведения ограниченного доступа или KYC-документы через публичные методы.

Реализация, заявляющая L5, SHOULD предоставлять:

- `GET /v1/compliance/profile` - машиночитаемый профиль контроля и отчетности;
- `GET /v1/compliance/consents` - статусы согласий и полномочий доступа без раскрытия лишних данных;
- `GET /v1/compliance/audit-events` - нормализованные события аудита для защищенных интеграций;
- `GET /v1/reports/regulatory` - перечень отчетных наборов, статусы подготовки и ссылки на защищенный контур получения.

L5 разделяет четыре уровня:

| Уровень | Назначение |
| --- | --- |
| Согласие | Кто, на что, на какой срок и с каким объемом полномочий дал согласие |
| Статус проверки | Машинный статус проверки без раскрытия внутренней методики |
| Аудиторский след | События с неизменяемыми идентификаторами, временем, типом и ссылкой на объект |
| Описание отчетности | Состав отчетности, период, статус, правовой контур и способ защищенного получения |

В российском контуре L5 должен учитывать открытые API и согласия клиента, AML/CFT, персональные данные, валютный контроль, цифровой рубль, ЦФА/ООЦФА и правила конкретной площадки.

## 15. Правомочия и авторизация (`Entitlements & Authorization`)

Профиль SHOULD публиковать `GET /v1/entitlements/capabilities`.

Этот слой описывает не юридическое заключение и не самостоятельное возникновение права, а безопасный API-контракт для проверки правомочий:

- типа правомочия (`entitlement`) или полномочия;
- держателя в псевдонимизированной форме;
- правового контура и правил площадки;
- ограничений, обременений, статуса и ссылок на доказательства;
- требуемой аутентификации;
- правил авторизации и делегированных полномочий;
- аудиторского следа и средств подтверждения авторства и целостности действия.

Профиль MUST запрещать чувствительные действия по умолчанию. Передача, обременение, погашение, делегирование или просмотр доказательств SHOULD требовать сильную аутентификацию, подпись запроса, временную метку или одноразовое значение, защиту от повторного воспроизведения, ограниченные полномочия, усиленную проверку и событие аудита.

Для HMAC-подписи приватных REST-запросов базовая строка подписи: `timestamp + method + path + canonical_query + sha256(body)`. `canonical_query` сохраняет все пары параметров, включая повторяющиеся: имена и значения кодируются в UTF-8 и процентном кодировании по RFC 3986, пробел передается как `%20`, затем закодированные пары сортируются побайтово по имени и значению. Хеш тела вычисляется по точным передаваемым байтам. Промышленная реализация MUST проверять подпись, окно временной метки, одноразовое значение или кеш защиты от повторов, полномочия ключа и требуемый уровень аутентификации до оценки действия.

Профиль MUST отклонять записи правомочий (`entitlements`), условия и действия, которые являются незаконными, дискриминационными, ущемляющими неотчуждаемые права, нарушающими персональные данные или обходящими AML/KYC, investor access, валютный контроль, санкционные, договорные или платформенные ограничения.

Минимальные методы:

- `GET /v1/entitlements/capabilities` - поддерживаемые типы правомочий, методы аутентификации, модели авторизации и меры безопасности;
- `GET /v1/entitlements` - правомочия и полномочия, видимые аутентифицированному субъекту;
- `POST /v1/entitlements/authorization/evaluate` - проверка допуска к действию без выполнения самого действия.

Обычный ответ по правомочию (`entitlement`) SHOULD содержать ссылки на доказательство, хеш, запись реестра и защищенную выдачу документа, но не должен раскрывать исходные документы, паспортные данные, банковскую тайну, персональные данные или охраняемую тайну через обычный API-ответ.
