# Governance

Цель governance: сохранить профиль открытым, нейтральным, проверяемым и пригодным для независимых реализаций.

## Роли

**Maintainers** отвечают за целостность спецификации, совместимость и release process.

**Implementers** внедряют профиль у участников рынка, в SDK и инфраструктурных системах.

**Reviewers** проверяют security, legal, market structure и developer experience.

**Legal reviewers** проверяют, что текст и API-контракт не создают ложного впечатления о праве деятельности, доступности продукта или допустимости обработки данных.

## Изменения

Каждое существенное изменение проходит через proposal:

1. Problem statement.
2. Proposed contract.
3. Backward compatibility.
4. Security impact.
5. Legal and data-governance impact.
6. Conformance impact.
7. Migration path.

Существенное изменение `MUST`-требования должно опираться хотя бы на один воспроизводимый сценарий и conformance-критерий. Для включения в стабильный профиль желательно подтверждение двумя независимыми реализациями либо одной реализацией и публичным техническим разбором.

## Версионирование

Стандарт использует SemVer:

- patch: исправления текста, не меняющие контракт;
- minor: совместимые расширения;
- major: breaking changes.

## Расширения

Vendor-specific расширения допустимы только через `extensions`. Они не должны менять смысл обязательных полей.

## Compatibility Claims

Реализация может заявлять уровень:

- `RU-DMIP L0`;
- `RU-DMIP L1`;
- `RU-DMIP L2`;
- `RU-DMIP L3`;
- `RU-DMIP L4`;
- `RU-DMIP L5`.

Заявление уровня должно содержать версию профиля, дату проверки, охваченные capabilities и ссылку на conformance report. Оно не должно выглядеть как сертификация, лицензия, правовой допуск или одобрение государственного органа.

Для материалов и machine-readable отчетов используется идентификатор `RU-DMIP`.

## Пилоты И Публичность

Участник пилота самостоятельно определяет, какие результаты могут быть опубликованы. Название организации, персоналии, цитаты, логотипы и вывод о поддержке проекта не публикуются без явного согласия.

Обезличенный технический результат может включать:

- проверенный сценарий;
- найденную неоднозначность контракта;
- предложение к схеме или тесту;
- измеримый эффект для следующей интеграции;
- нерешенный риск без указания источника.
