# Стратегия Продвижения Открытого Профиля Совместимости

Главная мысль: продвигать нужно не монополию библиотеки, а открытую совместимость инфраструктуры. SDK должен выигрывать качеством, простотой и готовностью, а не административным принуждением.

## Неправильный Старт

Плохая позиция:

> Обяжите всех использовать мою библиотеку.

Почему это слабая позиция:

- создает политическое и юридическое сопротивление;
- выглядит как частный интерес вместо инфраструктурного решения;
- делает проект зависимым от одного исполнителя;
- снижает доверие бирж, брокеров, банков и разработчиков.

## Правильный Старт

Сильная позиция:

> Рынку нужен единый открытый API-профиль, проверяемый conformance tests. SDK - это open-source reference implementation, которую можно использовать добровольно, потому что она уже работает.

Так проект воспринимается как инфраструктура, а не как просьба о привилегии.

Более точная версия для Draft 0.5:

> Рынку нужен единый проверяемый язык взаимодействия: роли участников, capabilities, execution semantics, entitlements/auth, consent, AML/KYC boundary, audit events, regulatory reporting metadata и conformance tests.

## Шаг 1. Оформить Технический Draft

Название:

- **RU Digital Market Interoperability Profile** - имя верхнего уровня;
- **RU-DMIP** - короткое техническое имя;
- **RU-DAX Interoperability Profile** - exchange/trading core и исторический alias;
- **SpreadX SDK** - reference implementation.

Состав draft:

1. REST API.
2. WebSocket market data.
3. WebSocket private events.
4. FIX-compatible profile для профессиональных участников.
5. Единая модель ордеров.
6. Единая модель сделок.
7. Единая модель балансов.
8. Единая модель ошибок.
9. Единая модель комиссий.
10. Единая модель лимитов.
11. Sandbox/testnet.
12. Conformance tests.
13. L5 Compliance & Reporting.
14. Universal Execution Semantics.
15. Entitlements & Authorization.

## Шаг 2. Сделать Reference Implementation

Минимальный пакет:

- Python SDK;
- TypeScript SDK;
- OpenAPI schema;
- JSON Schema;
- Postman collection;
- conformance test suite;
- reference mock venue.

Цель SDK: быть самым простым и понятным способом попробовать профиль, пройти тесты и начать внедрение.

## Шаг 3. Написать White Paper

Рабочее название:

**Единый открытый API-профиль для цифровой рыночной инфраструктуры**

Структура:

1. Проблема фрагментации API.
2. Риски для надзора, инфраструктуры и участников.
3. Международные аналоги.
4. Предлагаемая архитектура.
5. Требования безопасности.
6. Модель совместимости.
7. План пилота за 6 месяцев.
8. Universal execution semantics.
9. Entitlements and authorization contour.
10. L5 compliance/reporting контур.
11. Выгоды для государства, бирж, брокеров, банков, разработчиков и пользователей.

## Шаг 4. Вести Диалог Не С Одним Адресатом

Адресаты для обсуждения:

1. Биржи и брокеры.
2. Банки и финтех-компании.
3. Custody и wallet-провайдеры.
4. Market makers и профессиональные участники.
5. Разработчики торгового, учетного и риск-менеджмент ПО.
6. Compliance, RegTech и audit-команды.
7. ОИС ЦФА и ООЦФА.
8. Отраслевые ассоциации.
9. Банк России и профильные государственные органы после подготовки пилотного пакета.

Порядок важен: сначала техническая состоятельность и пилот, затем регуляторная формулировка.

## Юридически Аккуратная Формула

Цель не в том, чтобы закрепить конкретную библиотеку. Цель в одном из трех уровней:

| Цель | Реалистичность | Эффект |
| --- | --- | --- |
| Принцип единого открытого API в публичной политике | Средняя | Высокий |
| Технические требования в акте регулятора | Средняя/высокая | Очень высокий |
| SDK как open-source reference implementation | Высокая | Максимальный вход на рынок |

Оптимальная последовательность:

1. Проект публикует нейтральный draft.
2. Участники рынка обсуждают модель и edge cases.
3. SDK и mock venue доказывают реализуемость.
4. Conformance tests показывают проверяемую совместимость.
5. Пилот формирует факты для правовой и регуляторной дискуссии.

## Что Уже Закрывает Репозиторий

Репозиторий закрывает технический минимум:

- описывает API-профиль;
- публикует white paper;
- дает OpenAPI и JSON Schema;
- дает Python и TypeScript SDK;
- дает mock venue;
- дает conformance tests;
- показывает путь внедрения от L0 до L5.

Правильная следующая цель: превратить draft в пилотный пакет с реальными участниками и публичными conformance reports.
