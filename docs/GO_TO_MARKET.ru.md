# Внедрение И Отраслевой Пилот

Этот документ описывает путь от открытого draft к проверенной межсистемной совместимости. Он не является планом продажи SDK или получения формального статуса проекта.

## Единица внедрения

Минимальная единица внедрения RU-DMIP — не весь стандарт, а один:

- участник;
- сценарий;
- уровень совместимости;
- набор схем;
- набор conformance tests;
- отчет о расхождениях.

Такой подход позволяет проверять пользу до крупных архитектурных и организационных решений.

## Этап 1. Техническая оценка

Участник выбирает сценарий из [PILOT.ru.md](PILOT.ru.md) и отвечает на пять вопросов:

1. Совпадают ли сущности и идентификаторы?
2. Однозначны ли состояния и события?
3. Достаточны ли security controls?
4. Какие элементы должны остаться implementation-specific?
5. Можно ли повторно использовать контракт при следующем подключении?

Результат — короткий gap report, а не обязательство внедрять профиль.

## Этап 2. Закрытая рабочая сессия

Оптимальный состав:

- владелец API или корпоративный архитектор;
- владелец выбранного бизнес-сценария;
- специалист по информационной безопасности;
- legal/compliance для правозначимых данных и действий;
- maintainer профиля.

Сессия рассматривает только синтетические или обезличенные данные. Внутренняя архитектура раскрывается лишь в объеме, необходимом для объяснения границы контракта.

## Этап 3. Исполняемый пилот

Для одного сценария создаются:

- mapping внутренних сущностей на RU-DMIP;
- минимальный adapter или contract fixture;
- conformance tests;
- negative-path проверки;
- отчет о поддержанных capabilities;
- перечень необходимых расширений.

Пилот должен запускаться повторно и давать одинаковый результат.

## Этап 4. Вторая реализация

Совместимость приобретает рыночную ценность после проверки как минимум на двух независимых реализациях. На этом этапе измеряются:

- доля повторно используемой клиентской логики;
- число обязательных extensions;
- время подключения второй реализации;
- различия в семантике состояний;
- количество проблем, обнаруженных тестами до интеграционного запуска.

## Этап 5. Публичный профиль

Публиковать следует только обезличенные результаты:

- версию профиля;
- поддержанный уровень;
- список пройденных тестов;
- известные исключения;
- дату проверки;
- ссылку на воспроизводимый отчет.

Название организации или заявление о поддержке проекта публикуется только с ее явного согласия.

## Каналы участия

| Формат | Когда подходит | Результат |
| --- | --- | --- |
| Issue | точечная неоднозначность или недостающее поле | обсуждаемое изменение |
| Pull request | готовое обратно совместимое улучшение | проверяемая редакция |
| Private gap report | внутренняя модель или чувствительный сценарий | обезличенный proposal |
| Рабочая сессия | разногласие в семантике нескольких участников | согласованный сценарий |
| Исполняемый пилот | нужно измерить повторное использование | conformance evidence |

## Критерии качества внедрения

Профиль полезен, если он:

- уменьшает объем специальной логики клиента;
- обнаруживает неоднозначность до production;
- не вынуждает участника раскрывать внутреннее устройство;
- не смешивает техническую совместимость с правом деятельности;
- позволяет отказаться от неподходящего модуля;
- сохраняет возможность конкурировать продуктом, ценой и технологией;
- дает воспроизводимый результат третьей стороне.

## Что не считать успехом

- число отправленных писем;
- устное согласие без сценария;
- демонстрацию только reference sandbox;
- прохождение тестов, написанных под одну реализацию;
- публикацию badge без отчета;
- формальное упоминание проекта без независимой проверки.

## Следующий практический шаг

Для первого участника достаточно выбрать сценарий 1 или 2 из [PILOT.ru.md](PILOT.ru.md), провести mapping и добавить один внешний fixture в conformance suite. Это дает предметный результат быстрее, чем обсуждение полного стандарта.
