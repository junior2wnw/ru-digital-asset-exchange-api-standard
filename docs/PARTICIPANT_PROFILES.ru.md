# Профили Участников Рынка

Версия: Draft 0.3

Цель этого документа - сделать RU Digital Market Interoperability Profile полезным не только для биржи или SDK, а для каждого участника инфраструктуры: банка, брокера, оператора информационной системы, оператора обмена ЦФА, custody-провайдера, market maker, issuer, compliance-команды, разработчика и наблюдателя.

Профиль не дает лицензий, не заменяет правила площадки и не является юридической консультацией. Он задает общий API-язык, чтобы участник рынка мог быстро понять: какие роли поддерживаются, какие действия доступны, какие данные нужны, какие правовые ограничения должен проверить конкретный оператор.

## 1. Главный Принцип

Один API-контракт не должен заставлять всех быть одинаковыми.

Участники рынка отличаются статусом, лицензиями, клиентскими сценариями и обязанностями. Поэтому RU-DMIP разделяет:

- техническую совместимость;
- роль участника;
- заявленный уровень API;
- применимый правовой контур;
- фактические capabilities конкретной площадки.

Для этого используется публичный endpoint:

```text
GET /v1/profile
```

Он показывает роли, уровни совместимости, включенные модули, legal profiles, data governance и статус возможностей: `supported`, `sandbox_only`, `planned`, `not_supported`.

## 2. Карта Участников

| Участник | Что ему нужно от API | Что должно быть явно видно |
| --- | --- | --- |
| Биржа / торговая площадка | Market data, ордера, сделки, комиссии, лимиты, outages, conformance report | Какие инструменты доступны, какой уровень L0-L5 заявлен, какие рисковые и правовые ограничения применяются |
| Брокер | Единый слой подключения к площадкам, клиентские лимиты, статусы ордеров, отчеты | Разделение клиентских счетов, idempotency, аудит, ошибки, suitability/investor access |
| Банк | Интеграция с цифровым рублем, открытыми API, валютным контролем, AML/KYC | Consent model, AML boundary, data governance, цифровой рубль, отчетность |
| ОИС ЦФА | Выпуск и учет ЦФА, пользователи, решения о выпуске, реестр операций | Роль `ois_cfa`, правовой контур `259-fz-cfa`, signed issuance artifacts, audit export |
| ООЦФА | Заключение сделок с ЦФА, правила обмена, допуск клиентов | Роль `ootsfa`, investor access, статус клиента, лимиты и правила обмена |
| Custodian / wallet-provider | Адреса, депозиты, выводы, custody transfers, travel rule/compliance metadata | Wallet lifecycle, address book, compliance review, запрет смешивать технический вывод и правовое разрешение |
| Market maker | Низкая задержка, FIX/profile, лимиты, массовые отмены, контроль риска | L4/FIX capability, rate limits, kill switch, instrument status |
| Issuer | Выпуск цифровых прав, раскрытие условий, жизненный цикл погашения | Issuance artifacts, investor restrictions, settlement model, audit trail |
| Compliance / RegTech | AML/KYC события, screening, санкционные и fraud-флаги, выгрузки | `aml_kyc`, `audit_export`, `regulatory_reporting`, объяснимые статусы операций |
| Аналитика / надзор | Нормализованные события, market data, статусы площадок, incident feed | Публичные данные, агрегируемые справочники, versioned schemas |
| Разработчик | Простая документация, SDK, mock venue, тесты совместимости | OpenAPI, JSON Schema, Postman, conformance tests, стабильные ошибки |

## 3. Вопросы, Которые API Должен Закрывать

**Кто я в этой интеграции?**

Клиент должен видеть не только базовый URL, но и роли площадки: `exchange`, `bank`, `ois_cfa`, `ootsfa`, `custodian`, `wallet_provider`, `market_maker`, `compliance_provider`, `developer_tool`.

**Что можно делать технически?**

Capabilities публикуются отдельно от ролей. Например, банк может поддерживать `open_api_consent` и `digital_ruble`, но не поддерживать `derivatives`; биржа может поддерживать L2 trading, но не иметь L3 wallet custody.

**Что можно делать юридически?**

Endpoint `/v1/profile` не выдает юридическое разрешение. Он показывает, какой правовой контур заявлен и где ответственность остается за реализацией: регистрация в реестрах, AML/KYC, персональные данные, валютный контроль, ЭПР.

**Как понять, кому доступен инструмент?**

У инструмента появляются law-aware поля:

- `legal_classification`;
- `regulatory_scope`;
- `investor_access`;
- `payment_use_allowed`;
- `jurisdiction`.

Эти поля не заменяют договор, правила площадки или закон. Они дают машинно читаемый сигнал для клиентов, фронтенда, risk engine и compliance.

**Как не ломать существующие интеграции?**

Новые поля совместимы с прежним контрактом. Клиенты должны игнорировать неизвестные поля, если они не меняют смысл обязательных полей.

## 4. Уровни Совместимости

| Уровень | Название | Для кого особенно важен |
| --- | --- | --- |
| L0 | Discovery & Profile | Все участники: понять возможности площадки до интеграции |
| L1 | Market Data | Биржи, брокеры, аналитика, market makers |
| L2 | Trading | Биржи, брокеры, market makers, риск-системы |
| L3 | Wallet & Custody | Custody, wallet providers, банки, compliance |
| L4 | Derivatives & FIX | Профессиональные участники, market makers, institutional desks |
| L5 | Compliance & Reporting | Банки, ОИС/ООЦФА, compliance, аудит, надзорные интеграции |

L5 не означает передачу персональных или банковских данных в публичный API. Он означает наличие нормализованного, защищенного и правомерного контура для отчетности, аудита, выгрузок и согласий там, где это разрешено.

L5 полезен именно там, где участники рынка обычно говорят на разных языках: кто дал согласие, какие data scopes действуют, почему операция ушла на проверку, какой отчет подготовлен, где ссылка на защищенную выгрузку, к какому правовому контуру относится документ.

## 5. Требования К Удобству

Площадка, которая хочет быть удобной для рынка, SHOULD:

- публиковать `/v1/profile`;
- явно разделять sandbox и production;
- объяснять, какие роли и capabilities доступны;
- поддерживать idempotency для команд;
- возвращать стабильные машинные ошибки;
- публиковать лимиты и комиссии в структурированном виде;
- давать conformance report;
- поддерживать audit trail;
- показывать legal classification инструментов;
- не скрывать правовые ограничения в свободном тексте;
- отделять пользовательские данные от рыночных данных;
- не требовать использования конкретного SDK.

## 6. Что Не Должно Попасть В API Без Проверки

- Персональные данные без правового основания и согласия, если оно требуется.
- Банковская тайна или иная охраняемая законом тайна в публичных endpoint.
- Намек, что цифровая валюта разрешена как средство платежа между резидентами вне допустимого режима.
- Универсальное утверждение, что продукт доступен неквалифицированному инвестору.
- Смешение mock/sandbox поведения с production-допуском.
- Обязательность конкретной библиотеки или vendor SDK.

## 7. Результат

Draft 0.3 закрепляет RU-DMIP как профиль совместимости инфраструктуры рынка. У каждого участника появляется понятное место в контракте, а правовые ограничения становятся видимыми до интеграции, а не после инцидента.
