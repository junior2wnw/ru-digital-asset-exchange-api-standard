# Позиционирование RU-DMIP

## Что это

RU Digital Market Interoperability Profile — открытый технический стандарт, который задает общие правила совместимости API разных участников цифрового финансового рынка на уровне данных, поведения и проверок.

Он описывает общую часть интеграции между торговыми площадками, банками, брокерами, операторами цифровых прав, кастодиальными и учетными системами, поставщиками данных и разработчиками.

В одном предложении:

> Участники сохраняют собственные технологии и продукты, но используют единый проверяемый язык для подключения внешних систем.

## Какую проблему он решает

Разные API отличаются не только адресами и названиями полей. Основные затраты появляются там, где сторонам приходится отдельно согласовывать:

- что означает каждое состояние;
- когда команда считается принятой или исполненной;
- как безопасно повторить запрос;
- как восстановить последовательность событий;
- какие данные можно считать актуальными;
- какие полномочия нужны для действия;
- где заканчивается техническая возможность и начинается правовое ограничение;
- как подтвердить совместимость до промышленного подключения.

Без общего контракта эти вопросы решаются заново в каждой интеграции и остаются скрытыми в адаптерах, инструкциях и частных договоренностях.

RU-DMIP делает повторяющуюся часть явной, версионируемой и проверяемой.

## Что предлагает проект

Проект объединяет четыре элемента:

1. **Единая семантика** — общий смысл объектов, состояний, событий и ошибок.
2. **Машиночитаемый контракт** — OpenAPI и JSON Schema.
3. **Рабочий пример** — эталонные клиенты, песочница и Postman collection.
4. **Доказательство совместимости** — исполняемые автоматические тесты.

Это принципиальное разделение: спецификация говорит, как должна вести себя совместимая реализация; эталонный код показывает один из способов; тесты проверяют результат. Ни одна библиотека не становится обязательной.

## Что меняется для рынка

| Участник | Практический результат |
| --- | --- |
| Поставщик API | одна внешняя модель вместо набора индивидуальных контрактов |
| Банк или брокер | клиентский слой и проверки можно использовать при следующем подключении |
| Торговая площадка или оператор | совместимость проверяется без раскрытия внутреннего устройства |
| Кастодиан или цифровой депозитарий | движение, учет и подтверждение актива имеют однозначный жизненный цикл |
| ОИС, ООЦФА или эмитент | права, ограничения и доказательства передаются структурированно |
| Разработчик | меньше специальной логики, зависящей от конкретного поставщика |
| Информационная безопасность | заранее определены подпись, повторы, полномочия и аудит |
| Комплаенс и аудит | статусы и причины решений становятся машиночитаемыми и воспроизводимыми |
| Отраслевая рабочая группа | обсуждается работающий контракт, а не только описание будущей системы |

Общий профиль не уравнивает участников. Конкуренция сохраняется в продукте, технологии, качестве сервиса, цене, скорости и управлении риском. Стандартизируется только повторяющаяся граница между системами.

## Почему подход остается универсальным

- участник сам объявляет поддерживаемые роли и возможности;
- внедрение возможно по уровням L0-L5 и отдельным сценариям;
- необязательные особенности размещаются в расширениях;
- внутренняя архитектура не раскрывается и не стандартизируется;
- торговые, учетные, кошельковые, отчетные и правозначимые операции используют одну модель совместимости;
- новые типы участников можно добавлять без изменения смысла уже существующих объектов;
- клиент принимает решения по заявленным возможностям, а не по имени поставщика.

## Безопасность и право

Приватные запросы подписываются, имеют ограниченное время действия и защищаются от повторного воспроизведения. Команды используют идемпотентность. Чувствительные действия требуют явных полномочий, усиленной аутентификации и аудита. Защищенные документы и персональные данные не должны попадать в обычные ответы API.

При этом профиль не выдает юридическое разрешение. Он отдельно показывает техническую возможность, заявленную роль, правовой контур и ограничения, которые должна проверить конкретная реализация.

Такой подход не подменяет законодательство или внутренний контроль участника. Он позволяет этим требованиям быть видимыми и однозначными для интеграции.

## Чем проект не является

RU-DMIP:

- не является официальным государственным стандартом или нормативным актом;
- не подтверждает лицензию, регистрацию, надежность или допустимость продукта;
- не заменяет правила информационной системы, площадки, реестра или договора;
- не требует использования конкретного SDK;
- не объединяет участников в одну платформу;
- не объявляет совместимость без исполняемой проверки;
- не связывает организацию с проектом без ее согласия.

## Как проверить ценность без большого внедрения

Первый шаг — не обсуждение стандарта целиком, а один сквозной сценарий:

1. выбрать реальную обезличенную операцию;
2. сопоставить ее сущности и состояния с RU-DMIP;
3. запустить соответствующие тесты;
4. отметить, что удалось использовать без изменений;
5. повторить сценарий на второй независимой реализации.

Если второй участник подключается быстрее первого, а смысл операции, безопасность и правовые границы остаются однозначными, профиль выполняет свою задачу.

Формат пилота и критерии оценки приведены в [PILOT.ru.md](PILOT.ru.md).

## Короткое публичное описание

```text
RU-DMIP is an open, testable API standard for interoperable digital market
infrastructure: shared semantics, schemas, reference clients, a sandbox, and
conformance tests for execution, custody, compliance, and authorization.
```
