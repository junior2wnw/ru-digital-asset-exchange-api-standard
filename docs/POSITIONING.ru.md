# Позиционирование RU-DMIP

## В одном предложении

RU Digital Market Interoperability Profile — открытый исполняемый контракт, который позволяет разным участникам цифрового рынка говорить на одном API-языке и подтверждать совместимость тестами.

## Проблема

Различия API — это не только разные URL и названия полей. Наибольшая стоимость возникает там, где по-разному трактуются:

- роли участника и доступные возможности;
- идентификаторы инструментов, заявок, операций и субъектов;
- состояния исполнения и порядок событий;
- поведение повторного запроса;
- качество и актуальность данных;
- ограничения, правомочия и уровень аутентификации;
- согласия, аудит и отчетные артефакты;
- граница между общим контрактом и внутренней логикой.

Каждая новая интеграция вынуждена заново согласовывать эти вопросы. RU-DMIP делает повторяющуюся часть явной, версионируемой и проверяемой.

## Предложение

Проект объединяет четыре слоя:

1. **Domain contract** — единая семантика объектов, состояний и событий.
2. **Machine-readable contract** — OpenAPI и JSON Schema.
3. **Reference behavior** — sandbox и reference clients.
4. **Proof** — conformance tests и отчеты о заявленном уровне.

Реализация может поддерживать только нужные роли и уровни. Vendor-specific возможности остаются допустимыми через extensions и не должны менять смысл базового контракта.

## Для кого

| Участник | Практическая ценность |
| --- | --- |
| Площадка или оператор | понятная внешняя граница и дешевле каждое следующее подключение |
| Банк или брокер | повторно используемый клиентский и операционный слой |
| Кастодиан или цифровой депозитарий | единый жизненный цикл активов, переводов и учетных подтверждений |
| ОИС, оператор обмена или issuer | структурированные правомочия, ограничения и evidence references |
| Поставщик данных или разработчик | стабильные модели и меньше venue-specific логики |
| Compliance, audit, RegTech | машинные статусы, события и защищенные ссылки вместо свободного текста |
| Ассоциация или рабочая группа | нейтральный предмет обсуждения, который можно запустить и проверить |

## Чем проект отличается

- описывает не только endpoint, но и смысл состояния или события;
- разделяет capabilities, техническую возможность и правовой допуск;
- покрывает торговый, учетный, кошельковый и отчетный контуры одной моделью совместимости;
- допускает поэтапное внедрение L0-L5;
- включает negative-path проверки безопасности;
- не требует раскрывать внутреннюю архитектуру;
- не требует принимать весь профиль для проверки одного сценария.

## Нейтральность

RU-DMIP:

- не является официальным стандартом или нормативным актом;
- не подтверждает лицензию, регистрацию или допустимость продукта;
- не заменяет правила информационной системы, площадки, реестра или договора;
- не требует использования конкретного SDK;
- не объявляет совместимость без исполняемой проверки;
- не называет организацию участником проекта без ее согласия.

SDK, sandbox и Postman collection — заменяемые reference implementations. Нормативным центром проекта являются спецификация, схемы и conformance behavior.

## Оптимальный путь внедрения

1. Выбрать один сквозной сценарий.
2. Сопоставить его с профилем без production-данных.
3. Зафиксировать gaps и границы реализации.
4. Автоматизировать несколько проверок.
5. Повторить сценарий на второй независимой реализации.
6. Только после этого обсуждать отраслевой профиль или нормативное применение.

Подробный формат — в [PILOT.ru.md](PILOT.ru.md).

## Короткое публичное описание

```text
Open, testable interoperability profile for digital market APIs: schemas,
reference clients, sandbox, and conformance tests for market data, execution,
custody, compliance, and entitlement authorization.
```

## Формула для технического обсуждения

> Не требуется заранее соглашаться с проектом. Выберите один реальный сценарий, запустите reference sandbox, сопоставьте контракт с вашей моделью и покажите, где профиль экономит интеграцию или мешает ей. Оба результата полезны для следующей редакции.
